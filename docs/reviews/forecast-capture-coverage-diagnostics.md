# 사전 예측 기록과 원본 보관 기록의 분리 감사

기준일: 2026-11-18 KST. 예측 모델 변경이나 성과 발표가 아닌 연구 데이터 품질 진단이다.

## 시작과 문제

Python main 6288f6c와 열린 역할 정리 문서 PR #19를 확인했다. Java #29의 공시 검색 및 웹 #13과 별개이며 다른 작업 트리의 미커밋 연구 파일은 수정하지 않았다. 기존 감사는 파일 무결성과 고유 예측 거래일을 셌지만, 예측이 없는 원본 보관 기록이 시간 조건 때문인지 검토된 거래일 달력의 범위 부족 때문인지 합계에서 바로 구분하지 못했다.

## 바뀐 코드와 이유

- scripts/audit_private_capture.py의 latest_capture: 무결성을 재검사한 최신 기록의 고정 상태 코드 capture_status를 반환한다. API 키, 객체 경로, 원본 가격이나 점수를 추가하지 않는다.
- 같은 파일의 capture_inventory: 모든 기록의 무결성을 검사한 뒤 예측을 포함한 기록 수, 원본만 있는 기록 수, 두 가지 보류 이유별 개수를 각각 집계한다. 같은 거래일의 중복 예측 기록은 기존처럼 독립 표본으로 세지 않는다.
- tests/integration/test_private_forward_archive.py: 중복 예측, 원본만 있는 복수 기록, 혼합 기록, 달력 부족을 합성 메모리 저장소에서 검증한다. 기존 변조 검출 시험을 유지한다.
- Review.md: 이번 기능의 읽을 경로와 이유, 검증 한계를 연결한다.

흐름은 S3 호환 저장소 읽기 → 각 원본·기록 해시와 시각 검사 → 예측 유무 분리 → 이유별 합계다. 쓰기·재수집·일정 변경·예측 조건 완화는 수행하지 않는다. 합계는 저장 기록 개수이며 예측 대상 미래 거래일 수나 독립 시험 표본 수가 아니다. forecast_index_count + snapshot_only_index_count는 audited_index_count와 같고, duplicate_forecast_index_count는 forecast_index_count - unique_origin_session_count다.

## 이해를 위한 합성 예시

예측 기록 2개가 같은 거래일이고 시간 조건을 놓친 원본 보관 기록 3개가 있으면, 전체 기록은 5개지만 고유 사전 예측 거래일은 1개다. 이번 추가 출력은 예측 기록 2개, 원본만 보관 3개, 시간 조건 미충족 3개로 표시한다. 파일 5개를 새 예측 5건으로 해석하지 않는다. 달력이 부족한 기록은 시간 조건 실패와 별도 집계한다.

## 중간 오류와 검증

처음 작성한 시험의 반복문 lambda가 루프 변수를 늦게 참조할 수 있어 Ruff B023에 걸렸다. 기본 인수로 값을 고정했다. 새 금융 수식·모델·거래일 달력을 바꾸지 않았다. 로컬 및 원격 최종 검증 결과는 아래 완료 항목에 기록한다. 합성 저장소 시험은 실제 R2 비밀 설정을 사용하지 않는다.

## 한계와 다음 판단

GitHub 예약이 등록돼 있거나 작업이 성공했다고 예측 표본이 증가한 것은 아니다. 원본 보관과 사전 예측, 채점 코드의 성공과 예측 성능, 연구 결과와 제품 수요를 분리한다. 본 기능은 시간 조건 실패의 원인을 실행 지연으로 확정하지 않는다. 공급 데이터의 마지막 거래일·작업 시작·객체 보관 시각을 함께 비교해야 한다. 독립 미래 정답에 대한 검증과 충분한 표본이 없으므로 성능 HOLD를 유지한다. 운영 배포·Java RAG·회원·채팅은 이번 변경 범위가 아니다.
