# 사전 위험 예측과 비공개 가격 빈티지 보관 리뷰

작성일: 2026-10-23. 기존 Actions에서는 TLT·SPY의 현재 수정가격 704거래일을 매번 새로 받은 뒤 러너와 함께 폐기했다. 이번에는 **예측에 사용한 전체 가격 버전, Alpaca 원본 응답, 정규화 파일, 보관 시각과 예측값**을 비공개 S3 버킷에 한 묶음으로 영속 보관할 수 있는 경로를 추가했다. 실제 버킷과 접근 자격증명은 아직 제공되지 않았으므로 **실제 외부 보관 성공이나 새 기간 성능을 주장하지 않는다.**

## 코드 구조와 판단 조건

- `collect_alpaca_prices.py`: 기존 원본·정규화 해시에 더해 각각의 불변 파일 경로를 manifest에 명시한다. 기존 수집기·분석기의 날짜와 오차 계산은 그대로다.
- `archive_forward_capture.py`: manifest의 TLT·SPY 가격 CSV와 원본 응답 봉투를 업로드 전에 전부 다시 읽는다. 파일 경로가 지정된 비공개 원본 디렉터리 밖이면 거절한다. 원본 봉투의 정규 바이트, 봉투 해시, 응답 바이트 해시, CSV 해시가 모두 일치해야 업로드한다. 수집 파일과 manifest는 `SHA-256(manifest)` 아래에 보관하고 `If-None-Match: *`로 덮어쓰기를 막는다. 재시도에서는 이미 저장한 파일의 크기·해시를 비교하며, 다른 내용이 있으면 오류로 중단한다. 업로드할 때 SSE-S3 암호화를 요청한다. 실행 명령은 버킷의 네 가지 Public Access Block 설정을 모두 확인한다.
- `forward_risk_capture.py`: 예측 시각이 해당 가격 파일의 실제 수신 이후이면서 다음 거래일 **정규장 개장 전**이고, 가격 이력이 100개 이상의 과거 수익률을 제공할 때에만 5·20일 EWMA·최근 변동성·GARCH·GJR 예측을 만든다. 실제 S3 기록 경로인 `archive_forward_capture.py`는 **다음 개장보다 최소 1시간 전**에 원본 업로드가 끝난 경우에만 예측을 기록한다. 이 여유는 업로드 후 기록 시간을 위한 것이며 정확한 가격 게시 시각을 역산하지 않는다. 시간이 부족하면 원본만 보관하고 예측값은 0개로 명시한다.
- `score_forward_risk_record`: 다른 시각에 실제로 수집한 전체 가격 스냅샷에서 **20일 미래 구간까지 종가가 끝난 뒤**에만 5·20일 정답과 오차를 계산한다. 예측 때의 해시와 정답 가격 파일의 해시·수신 시각을 분리한다. 현재는 개별 사전 예측 기록의 검증 함수이며, 다수 기록의 독립 성능 집계나 공개 API는 추가하지 않았다.
- `.github/workflows/private-forward-capture.yml`: 기존 공개 로그 중심의 탐색 workflow와 별개로 수동 실행 가능한 비공개 보관 경로를 정의했다. 버킷·리전·접근키가 없으면 **가격 요청 전**에 실패한다. `boto3`는 이 작업에서만 사용하는 선택적 `archive` 의존성으로 추가했다. 이유는 조건부 S3 업로드와 저장된 객체의 해시·크기를 확인하기 위해서다.

비공개 보관을 실행하려면 GitHub 저장소의 변수 `SHOCKGRAPH_ARCHIVE_BUCKET`, `SHOCKGRAPH_ARCHIVE_REGION`과 비밀값 `SHOCKGRAPH_ARCHIVE_ACCESS_KEY_ID`, `SHOCKGRAPH_ARCHIVE_SECRET_ACCESS_KEY`를 설정해야 한다. 버킷의 Block Public Access 네 항목을 모두 켜고 대상 prefix에 한정한 `PutObject`, `GetObject`(HEAD 확인), `GetBucketPublicAccessBlock` 권한이 필요하다. 실제 보관 이후 버킷 버전 관리·보존 정책과 공급원 데이터 사용 범위를 별도 검토해야 한다. 원본이나 접근 자격증명은 공개 저장소·Actions 아티팩트에 업로드하지 않는다. [AWS의 조건부 쓰기 설명](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)에 따라 동일 객체 키의 덮어쓰기를 조건부 요청으로 막는다.

GitHub의 `workflow_dispatch`는 workflow 파일이 기본 브랜치에 있어야 실행된다. 따라서 이 기능 브랜치의 PR만으로 새 보관 작업을 수동 실행할 수 없고, 코드를 기본 브랜치에 반영하고 위 비공개 설정을 연결한 후 첫 실수집을 확인해야 한다. 자동 반복 일정은 추가하지 않았다. [GitHub의 workflow 이벤트 문서](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)를 따른다.

## 정확성·검증 범위

단위 시험은 5·20일 예측이 다음 거래일 정규장 개장 전에 기록되고, 미래 20일의 마지막 종가와 **나중에 수신한** 가격 파일이 없으면 채점이 거절되는지 검사했다. 미래 마지막 종가를 수정해도 이전에 만든 예측 원본 해시는 고정되고, 20일 정답만 달라지는지도 검사했다. 비공개 저장 통합 시험은 실제 파일 구조를 모사한 두 종목 manifest로 원본 손상과 디렉터리 이탈을 거절하고, 첫 쓰기와 동일 입력 재시도, S3 보관이 개장 직전으로 늦어진 상황의 예측 차단을 확인했다. 버킷 변수가 없으면 CLI가 가격이나 외부 서비스를 읽기 전에 `private_archive_not_configured`로 종료하는지도 검사했다. `make quality PYTHON=.venv/bin/python`에서 Ruff 위반 0건과 Pyright 오류·경고 0건, `make test PYTHON=.venv/bin/python`에서 전체 **172개 시험 통과**를 확인했다. [기존 Alpaca 수집 Actions 실행](https://github.com/AnDev77/ShockGarph_AI/actions/runs/39910307621)은 새 manifest를 포함한 실제 TLT·SPY 각 705거래일 수집과 탐색 분석에 성공했다. 이 실행은 **새 비공개 S3 보관 작업을 실행한 증거가 아니다.**

이 시험은 가짜 S3와 합성 가격으로 저장 계약을 확인한 것이다. **실제 개인 버킷에 저장된 빈티지는 0개, 채점 가능한 새 사전 예측도 0개**다. 따라서 앞서 본 2026년 가격 모델의 제품 성능 판정은 `HOLD`다. 2026년까지만 검증된 Nasdaq 달력은 2027년 이후 사전 예측을 만들기 전에 공식 달력으로 연장해야 한다. 공급원 약관·정규화 가격의 시점별 수정 범위도 운영 전에 검토한다.

## 독립 관점의 타당성 점검

| 판단 항목 | 실제 달성 | 제3자 판정 |
| --- | --- | --- |
| 작업 진행량 | 원본 검증·조건부 저장·예측 시각 제한·나중 채점 함수와 합성 통합 시험을 추가했다. 기존 실제 수집도 새 manifest로 통과했다. | **기반 구현은 실질적**이다. 그러나 새 S3 저장, 반복 수집, 채점 자동화는 완료되지 않아 운영 성과로 세면 과장이다. |
| 예측 방법 | 종목별 5·20일 기준선과 GARCH·GJR를 동일한 원점 가격에 적합하고 미래 정답은 별도 가격본에서 읽는다. | **사전 평가 설계로는 합당**하다. 현재 가격 이력 한 벌로 이미 확인한 성능을 독립 검증으로 주장할 근거는 없다. 복잡한 모델 우위도 미확정이다. |
| 누수와 재현성 | 개장 전 수신·보관된 가격 해시를 기록하고 다음 20거래일 종가가 수집되기 전에는 채점하지 않는다. | 과거 수정가격으로 과거 예측을 복원하는 오류를 피하는 방향이다. 수집 공급원의 실제 가격 이용 시각, 실제 S3 동작과 버킷 삭제 방지 정책은 별도로 검증해야 한다. |
| 제품 가치 | 사용자에게 보일 수 있는 새로운 검증 예측 수 0, 실제 사전 기록 0, 성숙한 새 기간 점수 0이다. | **아직 입증되지 않았다.** 개발 완료나 기존 Actions 성공을 방문 가치나 모델 성능으로 해석할 수 없다. |

다음 판정의 선행 조건은 비공개 버킷 설정과 실제 첫 기록, 개장 전 반복 실행, 이후 성숙한 5·20일 정답의 독립 집계다. 현재 workflow는 수동 실행이며 기본 브랜치 반영 전에는 새 작업을 시작할 수 없다. 실제 기록 시각이 개장 전이라는 조건은 원본 저장 후 확인하지만, 모델 계산과 최종 index 업로드의 완료 시각까지 별도로 측정하지 않으므로 첫 운영 실행에서 기록 완료 시각도 감사해야 한다.
