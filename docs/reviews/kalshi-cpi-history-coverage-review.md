# CPI 사건별 확률곡선 커버리지 감사

작성일: 2026-10-06. 브랜치: `feat/analytics`.

## 완료한 기능과 목적

한 사건에서 성공한 다중 임계값 분포를 전체 발표 목록에 적용할 때 표본이 얼마나
남는지 점검하는 오프라인 감사 도구를 구현했다. 자료가 없는 발표도 분모에 남긴다.
새 리뷰 이름은 핵심 기능으로 작성하도록 `AGENTS.md`와 리뷰 안내를 수정했다.
기존 일차별 파일과 링크는 보존한다.

| 파일 | 역할 |
|---|---|
| `scripts/audit_cpi_curve_history.py` | 발표 목록·사건별 원본 호가 행·컨센서스 빈티지 대조 |
| `tests/unit/test_cpi_curve_history.py` | 시점·품질·누락·중복·단조 보정·멱등성 검증 |
| `.github/workflows/alpaca-cpi-validation.yml` | 일반 검증과 실제 외부 자료 수집 분리 |
| `docs/troubleshooting/kalshi-data-use-authorization.md` | 기술적 접근과 연구 이용 허가 구분 |

## 감사 방법

1. 입력 발표 목록을 UTC 발표시각 순서로 정렬한다. 사건 ID와 계약 사건 식별자는
   각각 유일해야 한다. 목록 밖의 감사 자료와 중복 빈티지는 명시적으로 실패시킨다.
2. 공통 기준시점은 실제 BLS 발표 5분 전이다. 다른 기준시점의 보고서는 제외한다.
   호가는 기준시점 이후일 수 없고 실제 발표 전 15분 이내여야 한다.
   따라서 기본 설정의 기준시점 대비 최대 호가 나이는 10분이다.
3. 계약 정의·티커·임계값·확률 범위·UTC·해시 형식·스프레드 0.10 이하·양의 거래량을
   다시 검사한다. 후보 수·재고 수·제외 사유 집계와 실제 행 수도 대조한다.
4. 저장된 `distribution`을 신뢰하지 않고 유효 호가에서 단조 곡선을 다시 만든다.
   임계값 두 개 이상을 요구하며 최대 보정량 0.05 초과 시 해당 사건은 기권한다.
   이 한도는 품질 정책이며 통계적 유의성 기준이 아니다.
5. 정확히 0.1 간격으로 인접한 경계가 있을 때 계산 가능한 중심값 후보만 표시한다.
   예를 들어 0.2·0.3·0.4 계약은 중심값 후보 0.3·0.4를 지원한다.
   실제 전문가 예측이 0.3이라는 뜻은 아니다.
6. 실제 발표 전 컨센서스 빈티지가 제공된 경우에만 그 값의 경계·가용시각을 검증한다.
   경계가 없거나 컨센서스가 늦으면 기권한다. CPI 실제값과 ETF 수익률은
   품질 선정이나 중심값 후보 생성에 사용하지 않는다.

합성 사건 4건의 실행 결과는 다음과 같다. 실제 시장 관측 결과가 아니다.

| 합성 사례 | 결과 |
|---|---|
| 원래 단조인 곡선 | 유효 |
| 작은 역전이 있는 곡선 | 최대 0.01 보정 후 유효 |
| 큰 역전이 있는 곡선 | 보정 한도 초과로 기권 |
| 보고서 없는 발표 | `missing_curve_report`로 유지 |

총 4건 = 유효 2건 + 기권 1건 + 자료 누락 1건. 컨센서스는 4건 모두 미제공이다.
검증된 계약 재고 3건에서 호가 상태 `eligible` 9행이 집계되지만, 독립 발표 9건은 아니다.

## 실행과 산출물

```bash
make research-cpi-curve-history-demo
```

결과는 `artifacts/cpi-curve-history/<내용 SHA-256>/report.json`이다.
입력 해시·설정·합성 여부·사건별 상태를 기록하고 동일 입력 재실행은 같은 파일을 만든다.
새 CLI에는 HTTP 호출이나 자동 재수집 경로가 없다.

이용 허가가 실제로 확인된 이후의 오프라인 입력 방식:

```bash
python scripts/audit_cpi_curve_history.py \
  --releases /외부자료/release_vintage.csv \
  --curves-dir /외부자료/선택한-사건별-곡선 \
  --authorization-record /비공개자료/이용허가.txt
```

`--consensus`에는 `ConsensusVintage` 스키마의 JSON 배열을 선택적으로 넣는다.
그 `event_id`는 계약 사건 식별자와 맞춰야 한다. 전문가 컨센서스를 없을 때 만들지 않는다.
입력 디렉터리에 동일 사건의 여러 감사 실행이 있다면 사용할 빈티지를 먼저 명시적으로 선택한다.
CI의 축약 요약에는 원본 호가 행이 없으므로 이 도구의 입력으로 사용할 수 없다.

## 검증 결과

- 신규 테스트: 16개 통과.
- 전체 `make test`: 146개 통과. 기존 Starlette 테스트 클라이언트 사용 중단 예고 1건.
- `make quality`: Ruff 통과, Pyright 오류·경고 0건.
- 합성 CLI 두 번 실행 시 같은 경로·내용 확인.
- 발표 15분 전은 포함, 16분 전과 발표 후 호가는 제외.
- 과거 발표값·자산 수익률을 바꿔도 선택 결과가 바뀌지 않음.
- 로컬 Ruff 실행 파일 손상으로 초기 검사가 중단됐으나 같은 버전 0.16.9를
  재설치한 뒤 전체 검사를 통과했다. 저장소의 의존성 범위는 바꾸지 않았다.

## 실제 자료 실행과 한계

공식 이용조건에서 연구·개발·제품 이용 제한을 확인했다. 허가 근거 확인 전 이번
실제 재수집과 실자료 전체 감사는 실행하지 않았다. 상세 근거는
[이용 허가 점검](../troubleshooting/kalshi-data-use-authorization.md)을 참고한다.

- 구현·합성 검증 완료와 실제 전체 표본 감사 완료를 구분한다.
- 기존 `release_vintage.csv`는 이전 계약 감사에서 매칭한 발표 목록이다.
  모든 역사적 CPI 발표를 포함하는 모집단이 아니다. 입력 분모의 범위를 따로 보고해야 한다.
- 예전 `CPI-*` 계약도 입력 목록에서 누락 처리할 수 있다. 기존 실수집기는 `KXCPI-*`
  전용이므로 과거 접두사 수집 지원은 별도 구현·계약 검증이 필요하다.
- 캔들 종료시각을 역사적 가용시각으로 간주하는 기존 v1 가정을 결과에 표시한다.
  당시 수신시각을 증명하거나 저장된 원본 해시의 파일 내용까지 재검증하는 도구는 아니다.
- 희소한 사건·빠진 임계값을 임의 보간하거나 다른 사건의 호가로 채우지 않는다.
- 이번 결과는 예측 정확도 개선, 수익성 또는 연구 가설의 입증 결과가 아니다.

## 사용자가 볼 부분과 다음 작업

1. `status_counts`: 누락·기권을 포함한 합계가 입력 발표 수와 맞는지 확인한다.
2. 사건별 `curve_error`: 탈락이 시간·유동성·계약 오류·보정 과다 중 무엇인지 확인한다.
3. `exact_boundary_centers`와 `consensus_status`: 계산 가능한 후보와 실제 전문가
   컨센서스 가용성을 구분한다.
4. 실제 허가의 범위와 발표 전 전문가 컨센서스 공급원을 먼저 확인한다.

다음은 허용된 실제 사건별 자료로 같은 감사를 실행하고 SPY·TLT 교집합을 재계산하는
단계다. 이후 컨센서스·전통 정보 기준 모델과 Kalshi 추가 모델을 같은 사건에서
시간순 비교한다. 자료가 부족하면 지표를 비워 두고 이유를 보고한다.
