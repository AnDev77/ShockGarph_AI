# 데이터 분석 방법론

작성일: 2026-09-22

이 문서는 ShockGraph AI가 이벤트 확률을 자산 반응과 포트폴리오 위험으로 연결할 때
사용할 데이터 정의, 누수 방지, 평가 방법, 온라인 제공 기준을 정리한다.
모델 성능을 주장하려면 고정된 시험 분할, 독립 이벤트 수, 불확실성을 함께 공개해야 한다.

## 분석 대상과 단위

분석의 기본 단위는 `event_id`다. CPI 발표 한 건에 여러 시점의 시장확률 스냅샷이
있어도 독립 사건 수는 하나다. `market_ticker`는 특정 계약의 확률·결과를 식별하고,
`asset_id`는 반응을 측정할 종목을 식별한다.

분석 조합은 `(asset_id, event_category, horizon, currency, model_version)`으로 식별한다.
설정 파일의 후보 종목은 학습 완료 목록이 아니며, 표본·이용권·지원 기간을 확인한 조합만
화면과 API에서 `ready` 상태로 노출한다.

## 시각과 데이터 계보

각 관측은 다음 시각을 구분한다.

| 시각 | 의미 | 특징량 조건 |
|---|---|---|
| `source_time` | 가격·발표·계약이 가리키는 시각 | 원본 응답에서 보존 |
| `available_at` | 모델 입력으로 실제 이용 가능해진 시각 | 발표 시각·수집 정책 반영 |
| `observed_at` | 분석 스냅샷 기준시각 | 모든 입력의 상한 |
| `resolved_at` | 이벤트 결과가 확정된 시각 | 정답값 생성 경계 |
| `collected_at` | 시스템이 응답을 저장한 시각 | 원본 재현·장애 추적 |

모든 저장 시각은 UTC다. 특징량은 `feature_as_of <= observed_at < resolved_at`를 만족해야
하며, 실제 입력의 `available_at`이 기준시각보다 늦으면 사용할 수 없다.
현재 코드의 `observed_at`은 일부 데이터에서 수집 기준시각을 뜻하므로, 공급원 어댑터를
추가할 때 `available_at`과의 의미를 명시적으로 확장해야 한다.

원본 JSON, 원본 해시, 변환 버전, 데이터셋 체크섬, 모델 버전, 예측 기준시각을 연결해
결과 하나를 다시 만들 수 있어야 한다. 원본과 모델 산출물은 객체 저장소에 보존하고,
검증된 메타데이터·특징량·예측 결과는 PostgreSQL에 둔다.

## 확률 계층

Kalshi 계약의 시장확률은 이벤트가 발생할 확률이며 자산 상승확률이 아니다.
먼저 원시 시장확률을 그대로 반환하는 기준 모델을 만든다. 이후 이벤트별 시간순 분할을
적용한 로지스틱 또는 아이소토닉 회귀 보정 모델과 비교한다.

Brier 점수를 주요 지표로, 로그 손실과 기대 확률 보정 오차를 보조 지표로 사용한다.
동일 이벤트의 관측 자료가 서로 다른 분할에 들어가지 않게 한다.
확률 보정 모델은 같은 시험 표본에서 기준 모델보다 나은지 비교해야 한다.

### Brier 점수

`Brier = mean((p - y)^2)`에서 `p`는 예측확률, `y`는 0 또는 1인 실제 결과다.
낮을수록 확률 예측이 실제 결과에 가깝다. Brier 점수를 적중률이나 예상수익률로 해석하지 않는다.
각 보고서에는 점수, 표본 수, 신뢰구간, 분할, 모델 버전을 포함한다.

### 확률을 자산 반응으로 결합

서로 배타적인 시나리오 `s`가 있고, 이벤트 확률 `P(s)`와 자산 조건부 결과 `P(up | s)`가
있다면 다음처럼 결합한다.

`P(up) = Σ P(s) × P(up | s)`

기대수익률도 같은 시나리오와 기간에서 `E[R] = Σ P(s) × E[R | s]`로 결합한다.
중첩된 임계값 계약을 서로 배타적인 시나리오처럼 더하지 않는다. 시나리오 범위와
확률 합계가 1인지 확인하는 계약이 필요하다.

## 이벤트 연구 계층

이벤트 전 `[-120, -21]`거래일 구간에서 기대수익률을 추정하고,
`[-5, +5]`거래일 구간에서 비정상수익률과 누적 비정상수익률(CAR)을 보고한다.
이벤트 시각을 자산별 첫 거래 가능 세션에 맞춘다.

발표가 장중·장외인지, 현지 거래일과 UTC 날짜가 다른지, 휴장일·조기폐장일이 있는지 기록한다.
가격은 수정주가 여부, 통화, 수익률 계산 기준을 명시한다. 이벤트 단위 재표집으로
신뢰구간을 추정해 같은 이벤트의 여러 스냅샷을 독립 표본처럼 세지 않는다.

## 전이 분석 계층

희소한 시차 연관성을 사용하며 이를 인과효과로 표현하지 않는다.
각 연결에는 시차, 계수, 신뢰구간, 표본 수를 포함한다.

## 위험 계산 계층

시나리오 조건부 자산 수익률과 검증된 포트폴리오 비중을 결합한다.
기대수익률, 과거 자료 기반 VaR, 기대손실(Expected Shortfall), 자산별·이벤트별 기여도를 보고한다.
비중 합계, 통화, 가격 기준시각, 결측 자산을 검증한다. 미지원 자산을 몰래 제외하거나
나머지 비중을 자동으로 재정규화하지 않는다. 결과는 위험 정보이며 거래 권유가 아니다.

## 오프라인 학습과 온라인 제공의 분리

SQL 특징량 스냅샷은 오프라인 데이터셋 생성과 결과 재현의 기준이다.
온라인 포트폴리오 요청에서 원본 가격을 전체 조인하거나 학습을 실행하지 않는다.
승인된 모델 버전과 미리 계산한 예측 스냅샷을 읽고, 입력 조합과 기준시각을 확인한 뒤 제공한다.

Redis는 기준 저장소가 아니라 검증된 응답의 지연 로딩 캐시다. 권장 흐름은 다음과 같다.

1. 자산·이벤트·기간·기준시각·모델 버전·정규화 포트폴리오 해시로 캐시 키를 만든다.
2. 캐시 적중 시 응답의 기준시각·모델 버전·신선도 상태를 검증하고 반환한다.
3. 캐시 미적중 시 PostgreSQL의 승인된 스냅샷을 제한시간 안에 조회한다.
4. 같은 키의 동시 미적중은 단일 비행 lease로 한 요청만 채우게 한다.
5. 허용 가능한 오래된 결과가 있으면 `stale_at`과 함께 반환하고 최신화를 진행한다.
6. 결과가 없거나 너무 오래됐으면 숫자를 만들어내지 않고 `pending`, `stale`,
   `insufficient_data`, `unsupported` 중 적절한 상태를 반환한다.

캐시 미적중을 성공으로 간주하려면 다음 지표를 별도로 측정한다.

- 캐시 적중률과 키별 stampede 횟수
- 캐시 적중·미적중의 p50, p95, p99
- Redis 연결시간, DB pool 대기시간, 스냅샷 쿼리시간
- 오래된 응답 비율, timeout 비율, 상태별 오류율
- 모델 버전 불일치와 기준시각 만료 건수

초기 성능 가설은 전체 p95 500ms 이하로 두되, 캐시 적중과 미적중을 분리해 측정한다.
이 수치는 운영 보장이 아니라 부하 테스트의 시작점이다.

## 검증과 고도화 순서

- 단위: 확률 범위, UTC, 기준시점, 포트폴리오 비중, 캐시 키 정규화
- 계약: 모델 버전·표본 수·신뢰구간·데이터셋 체크섬이 응답에 포함되는지 확인
- 통합: Redis 적중·미적중, DB timeout, 오래된 응답 허용시간, 단일 비행 동작
- 부하: 동시 요청, DB pool 고갈, 큐 backlog, 캐시 stampede, p95·p99
- 배포: readiness, 점진 트래픽 이동, 회로 차단기 rollback, expand-contract migration

상용 배포는 Docker 이미지와 환경 변수 계약을 유지한 채 관리형 컨테이너에서 시작한다.
AWS 데이터 계층을 선택하면 ECS/Fargate, GCP 데이터 계층을 선택하면 Cloud Run을 우선 검토한다.
Kubernetes는 실제 운영 복잡도와 팀의 클러스터 관리 역량이 확인된 뒤 다시 평가한다.
