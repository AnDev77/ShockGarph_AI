기준: 2026-09-22 로컬 작업 브랜치. 이번 문서는 3~4일차 복습과 제품 설계 보완이며 5~6일차 구현 완료를 의미하지 않는다.

| 회차 | 주제 | 먼저 읽을 코드 | 직접 설명할 수 있어야 하는 내용 |

| 3 | 트랜잭션 아웃박스, 시계열 DB | `0001_ingestion.sql`, `0002_day03_04.sql` | DB 저장 후 메시지 전송 전에 죽으면 어떻게 되는가? |

## 3. 프로토콜 → 어댑터 → 도메인 로직

`CleanRepository`는 저장 방법이 지켜야 할 함수 형태를 정의한다.
`RawToCleanWriter`는 DB 종류를 직접 알지 않고 `write_once()`만 호출한다.
현재는 메모리 어댑터를 전달하며 나중에는 PostgreSQL 어댑터를 전달한다.

Java에 비유하면 인터페이스를 서비스에 주입하고 구현체를 교체하는 구조다.
Python 프로토콜은 명시적으로 상속하지 않아도 필요한 메서드 구조가 맞으면 타입 검사에서 호환될 수 있다.
프로토콜 선언 자체가 트랜잭션이나 실행 중 검증을 만들어 주지는 않는다.

실습:

1. `test_normalization.py`를 실행하고 두 번째 호출의 `created=False`를 확인한다.
2. 저장소 객체를 새로 만든 뒤 재처리하면 다시 저장되는 이유를 설명한다.
3. DB 어댑터라면 멱등 키와 정제 데이터 행을 같은 트랜잭션에서 저장해야 하는 이유를 적는다.

## 4. 해시, 체크섬, 불변성, 멱등성

- 해시: 내용의 식별값. JSON 키 순서가 달라도 정규화 JSON이 같으면 동일하다.
- 체크섬: 저장한 실제 바이트가 바뀌지 않았는지 검증하는 값.
- 불변성: 동일 객체 키의 기존 내용을 바꾸지 않는다.
- 멱등성: 같은 작업을 재시도해도 최종 효과가 한 번 처리한 것과 같다.

이 저장소에서는 응답 본문 해시와 산출물 체크섬의 계산 대상이 다를 수 있다.
`LocalObjectStore` 체크섬에는 마지막 줄바꿈 바이트까지 포함된다.
따라서 이름이 모두 SHA-256이라는 이유로 두 값을 서로 대체하면 안 된다.

현재 멱등 키 입력은 `payload_hash + transformation_version + target_table`이다.
`v1`에서 `v2`로 변환 로직을 바꾸면 같은 원본을 다시 처리할 수 있다.
다만 같은 응답 본문이 다른 관측시각에 다시 나타나는 경우, 단순 내용 해시만으로는
관측 식별 정보를 충분히 표현하지 못한다. 원본 내용과 수집 발생 건을 구별하는 설계가 후속 과제다.

실습:

- 같은 키와 같은 응답 본문을 두 번 저장하고 `created`를 비교한다.
- 같은 키에 다른 응답 본문을 저장해 충돌 예외를 확인한다.
- 변환 버전을 바꿔 재처리하고 기존 변환 결과와 어떻게 구분되는지 설명한다.

## 5. 트랜잭션 아웃박스와 DB

DB 저장과 브로커 발행은 별도 시스템이므로 한쪽만 성공할 수 있다.
따라서 원본 저장 성공 후 메타데이터와 아웃박스 행을 하나의 DB 트랜잭션에 넣고,
발행기가 아웃박스를 읽어 발행한다. 발행은 성공했는데 완료 표시 전에 죽으면 재발행될 수 있다.
소비자의 멱등성이 필요한 이유다.

현재 SQL에 아웃박스 테이블이 있다는 사실과 이 흐름이 실행된다는 것은 다르다.
현재 `RawToCleanWriter`는 원본 저장이나 아웃박스 작성까지 책임지지 않는 별도 함수다.

TimescaleDB 하이퍼테이블은 시간 기준으로 데이터를 나누어 관리한다.
자산 가격의 키에 관측시각이 포함되는 이유와 범위 조회 인덱스를 살펴본다.
현재 Docker Compose는 일반 PostgreSQL 이미지이며 TimescaleDB 마이그레이션 실행 환경은 아직 없다.

실습 질문:

- 파일 저장 성공 후 DB 저장이 실패하면 원본은 어떻게 복구에 사용할 수 있는가?
- 중복 검사 후 삽입을 따로 실행하면 어떤 경쟁 조건이 생기는가?
- 원본 해시 하나가 여러 수집시각을 가질 때 현재 `raw_payloads` PK는 충분한가?

## 6. 시간은 적어도 세 가지로 나눠 생각하기

| 시각 | 의미 | 예 |
|---|---|---|
| 데이터가 가리키는 시각 | 경제지표 대상 월, 체결/종가 시각 | 8월 CPI, 금요일 종가 |
| 정보가 알려진 시각 | 발표 또는 사용 가능 시각 | 9월 CPI 발표 시각 |
| 시스템이 얻은 시각 | API 수집 완료 시각 | API 요청이 끝난 시각 |

과거 예측을 재현하려면 해당 예측 시점에 실제 이용 가능했던 정보만 사용해야 한다.
현재 코드의 `feature_as_of <= observed_at < resolved_at`는 일부 시간 관계만 검사한다.
`observed_at`이 수집시각인지 예측 스냅샷 시각인지 명확히 하고,
향후 원본 시각 / 이용 가능 시각 / 수집시각을 별도 계약으로 정해야 한다.

`trading_session_date()`는 현지 달력 날짜만 반환한다. 그 날짜가 개장일인지,
지금 장이 열려 있는지, 이벤트 뒤 첫 거래 가능한 세션인지까지 판단하지 않는다.
`latest_at_or_before()`도 오래된 마지막 값을 고를 수 있으므로 허용 지연시간 검사가 필요하다.

실습:

1. 동일 UTC 시각을 XNYS와 XKRX로 바꾸고 날짜 차이를 확인한다.
2. 미국 DST 전후 종가 UTC 시각이 어떻게 달라지는지 거래일 달력으로 확인한다.
3. 금요일 장 마감 후 발표 → 월요일 휴장인 경우 첫 거래일을 어떻게 찾을지 설계한다.
4. 과거 데이터의 수정주가가 미래 기업행동을 포함할 때 생길 수 있는 문제를 적는다.

## 7. 확률 보정과 가격 예측의 차이

Kalshi 확률은 특정 이벤트 계약의 YES 확률이다. 예를 들어 기준금리 인하 계약의 확률이며,
그 값이 QQQ 상승확률을 뜻하지 않는다.

시장확률 기준 모델은 입력 확률을 그대로 출력한다. 학습하지 않는다.
확률 보정 모델은 과거 예측과 실제 발생 결과를 이용해 확률의 과대·과소 추정을 보정한다.
가격 반응 모델은 별도로 이벤트별 자산 수익률을 추정해야 한다.

### Brier 점수 손계산

`Brier = mean((p - y)^2)`, 결과 `y`는 0 또는 1이다. 낮을수록 좋다.

| 예상확률 p | 실제 y | 제곱오차 |
|---|---|---|
| 0.8 | 1 | 0.04 |
| 0.7 | 0 | 0.49 |
| 0.2 | 0 | 0.04 |

평균은 `(0.04 + 0.49 + 0.04) / 3 = 0.19`다.
0.19를 적중률 81%라고 해석하면 안 된다.
비교는 동일한 평가 표본에서 시장확률 기준 모델과 보정 모델을 함께 수행한다.

### 이벤트 분할에서 주의할 점

동일 CPI 발표의 스냅샷 100개는 독립 이벤트 100개가 아니다.
이들을 학습·시험에 나누면 같은 사건이 평가 데이터에 새어 들어간다.
현재 이벤트 그룹화는 이 중복을 막지만 다음 문제까지 모두 해결하지는 않는다.

- 앞 분할의 정답값이 뒤 분할의 예측시점 전에 알려졌는지 별도로 검사해야 한다.
- 하나의 이벤트에 여러 임계값 계약이 있으면 YES/NO 결과가 계약마다 다를 수 있다.
  `event_id`는 분할 그룹, `market_ticker`는 정답값 대상이 되어야 한다.
  현재 데이터셋은 이벤트 하나에 결과 하나를 가정한다.
- 표본 1개에 현재 구간이 한 점으로 나오는 것은 확실한 예측이라는 뜻이 아니다.
- 동일 이벤트 반복 관측을 고려하는 이벤트 단위 군집 재표집이 필요하다.

### 이벤트 확률을 자산 반응에 연결하는 교육용 예

서로 배타적이고 전체를 포괄하는 두 시나리오 A/B만 있다고 가정한다.
아래 값은 모두 가상이며 실제 전망이 아니다.

- `P(A)=0.6`, `P(B)=0.4`
- `P(QQQ 상승 | A)=0.7`, `P(QQQ 상승 | B)=0.3`
- 혼합 상승확률: `0.6×0.7 + 0.4×0.3 = 0.54`
- 조건부 기대수익률이 A에서 +2%, B에서 -1%라면 혼합 기대수익률은 +0.8%

기간, 통화, 수익률 정의, 기준시각이 같아야 결합할 수 있다.
중첩된 임계값 계약을 배타적인 시나리오처럼 더하면 안 된다.
포트폴리오 VaR/ES는 자산 간 동시 움직임까지 필요하며 개별 상승확률만으로 계산할 수 없다.

## 8. 등록부에서 화면까지

모델 파일은 객체 저장소에, 버전·체크섬·평가 지표는 DB에 저장하는 목표다.
현재 등록부는 검증 계약과 스키마이며 등록·승격·서빙 서비스는 구현 전이다.

향후 화면 결과 하나는 종목, 이벤트, 기간, 기준시각, 모델 버전, 데이터셋 스냅샷,
독립 이벤트 수, 불확실성 방법으로 재현할 수 있어야 한다.
모델을 새로 학습했더라도 지원하지 않는 종목·기간의 숫자를 자동으로 표시하면 안 된다.

## 9. 내 PC에서 실행하기

이 대화 작업공간의 파일은 사용자 PC에 자동 복사되지 않는다.
실습 전에 이 변경분이 들어 있는 프로젝트를 PC로 가져와야 한다.

Windows PowerShell, 저장소 최상위에서:

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -e ".[dev]"
.venv\Scripts\python -m pytest tests/unit/test_object_store.py -q
.venv\Scripts\python -m pytest tests/unit/test_calibration_baseline.py -q
.venv\Scripts\python -m ruff check .
.venv\Scripts\python -m pyright
.venv\Scripts\python -m pytest
```

Linux/macOS에서는 `.venv/bin/python`을 사용한다.
실습 수정은 별도 브랜치에서 하고, 실패 원인을 설명한 후 고친다.
